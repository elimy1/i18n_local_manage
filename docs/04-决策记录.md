# 决策记录 D1–D4（M1 开工前必须定）

> 依据：[03-Spike结果.md](03-Spike结果.md) 的实测数据。三项决策的排序 = 对"产品能不能被信任"的影响权重。

---

## D1 · 键命名：三层确定性命名，禁用内容哈希

### 问题（实测）

vben 914 个键里 **681 个（74.5%）是 `auto.c8aefc2` 这种哈希键**，因为 slug 只认 ASCII。同时出现三种废键：

| 实际键 | 原文 | 为什么废 |
|---|---|---|
| `auto.a` | 选项A | ASCII 单词被截到 1 个字符，无意义 |
| `auto.a-a-a-a` | 回复了 `<a>杰克</a>` 的问题… | 富文本里的标签名被当成词 |
| `auto.c8aefc2` | 请输入（出现了 **41 次**） | 哈希键，看不懂、搜不到、改文案就废 |

而"请输入"这种串在项目里出现 41 次、共用一个键——这正是键命名最有价值的地方，也最容易被做烂。

### 候选方案

| 方案 | 可读性 | 确定性 | 稳定性（改文案后键是否失效） | 成本 |
|---|---|---|---|---|
| A. 内容哈希（现状） | ✗ | ✓ | ✗ 文案一改键就变 | 0 |
| B. 纯拼音 | △ `qingshuru` 可读性差、英文团队完全不懂 | ✓ | △ 同音歧义 | 低（pinyin-pro 97KB） |
| C. 纯 AI 命名 | ✓✓ `password.please-enter` | ✗ 每次调用可能不同 | ✗ 重跑就变 | 每串一次调用 |
| **D. 结构 + AI 语义 + 拼音兜底** | ✓✓ | ✓（结构层确定） | ✓（键写入即冻结） | 每"新串"一次调用 |

### 决策：采用 D

**键结构**（默认模板，可配）：

```
<namespace>.<scopePath>.<role>.<slug>
例：app.pages.user.list.placeholder.please-enter
```

| 段 | 来源 | 确定性 |
|---|---|---|
| `namespace` | 配置，默认 `app` | 用户定 |
| `scopePath` | 源文件相对路径（去 `src/`、`views/`、`pages/` 前缀）+ 文件名 | **完全确定** |
| `role` | AST 位置：jsx-attr→属性名；obj-prop→属性名；call-arg→callee 末段；jsx-text→`text` | **完全确定** |
| `slug` | ① 原文含 ASCII → 直接取词；② 纯中文 → AI 生成 2–4 词英文；③ 离线/无 AI → 拼音；④ 都失败 → `t_0001` 递增 | 分层降级 |

**三条硬规则**：

1. **键写入 catalog 即冻结**。二次提取、文案修改、AI 重跑都不得改动已有键——否则每次运行都产生 diff，用户会直接关掉这个功能。
2. **AI 只负责 slug 段，不负责路径段**。路径能提供 90% 的消歧能力（同名"编辑"在 user/list 和 role/list 下自动区分），也让 key 能反查文件。
3. **禁止内容哈希**。哈希键 = 不可读 + 不稳定的双重失败。

### 效果对比（真实数据）

| 原文（出现次数） | A 哈希（现状） | B 拼音 | D 结构+AI（决策） |
|---|---|---|---|
| 请输入（41×） | `auto.c8aefc2` | `auto.qingshuru` | `app.pages.user.list.placeholder.please-enter` |
| 请选择（18×） | `auto.cxxxxxx` | `auto.qingxuanze` | `app.components.select.placeholder.please-select` |
| 编辑（17×） | `auto.cxxxxxx` | `auto.bianji` | `app.pages.role.list.text.edit` |
| 访问来源（18×） | `auto.cxxxxxx` | `auto.fangwenlaiyuan` | `app.pages.dashboard.analysis.text.traffic-source` |
| 请再次输入新密码（18×） | `auto.cxxxxxx` | `auto.qingzaicit…` | `app.pages.profile.password.confirm-password.placeholder` |

注意最后一行：D 方案在"该串已被长路径完全描述"时**允许省略 slug**——键短且不冗余。这条规则要写进 prompt。

### 风险与回退

- 风险：AI 生成的 slug 风格漂移（同义不同词）。缓解：固定 few-shot + 词表约束（动词白名单：edit/delete/create/save…）+ 首次生成后冻结。
- 回退成本：**中**。键是 catalog 的一等公民，M2 之后回退要写迁移脚本。所以这一项必须在 M1 第一周定死。

## D2 · 句子建模：富文本整体抽取，宁缺勿错

### 问题（实测）

`<a href={href}>{owner}</a> 发布在 <a href={href}>{href}</a>` 只抽出"发布在"一个碎片。中文勉强能读，**英文语序直接崩**（"... published in ..." 的前后结构丢失）。同类还有：`万`、`元`、`{v0}月` 被单独成键（实测 8 例）。

### 候选方案

| 方案 | 正确性 | 实现成本 | 译者体验 |
|---|---|---|---|
| A. 只抽纯文本节点，跨元素不抽 | ✓ 不会错 | 0 | 差：大量文案抽不出来 |
| B. 富文本整体抽取，子元素 → 带索引占位符 | ✓ 语序完整 | 中 | 好：`<0>开源组</0> 创建了项目 <1>Vue</1>` |
| C. 强制用 `<Trans>` 组件 + ICU | ✓ | 高（要求目标项目已接 react-i18next Trans） | 最好，但侵入性强 |

### 决策：采用 B，并对"跨不跨"给出硬边界

**允许跨**：同一 JSX 父节点下、连续的文本节点与**内联元素**（`a/b/span/strong/em/code/i/s/Tooltip`），中间不含表达式分支。

**禁止跨**（直接不抽，进 review queue）：
- 条件表达式（`cond && <X/>`、三元）
- `.map()` / 循环体（每次迭代的文案应复用同一键）
- 组件边界（父组件把 children 传下去）
- 纯单位/量词碎片（`万`/`元`/`月`），除非能与相邻数字表达式绑定成 `{v0} 万`

**产物形态**：

```tsx
// 抽取后
t('app.pages.workspace.text.created-project', { 0: <a>{owner}</a>, 1: <a>{href}</a> })
// catalog
// "在 <0>{owner}</0> 创建了项目 <1>{href}</1>"
```

Vue 侧对应 `<i18n-t keypath="..." tag="span"><template #0>…</template></i18n-t>`。

### 风险与回退

- 风险：占位符索引与标签语义脱钩，译者看不懂 `<0>` 是什么。缓解：catalog 里保留 `placeholders: {0:"a", 1:"a"}` 元数据，编辑器里渲染成真实标签预览。
- 回退成本：**低**。若实现受阻，可退到 A（少抽但不抽错），不影响 catalog 结构。

## D3 · 扫描内存：流式 + worker 池 + 增量索引

### 问题（实测）

1495 个文件、1.02 秒扫描完，但 **RSS 292MB / heap 159MB**——因为全量 AST 都留在堆里。按此线性外推，1 万文件项目 ≈ 2GB，VS Code 扩展进程会直接被 OOM 杀掉。这是"能跑 demo、不能上生产"的典型差距。

### 决策：三件事一起做

| 措施 | 具体做法 | 验收 |
|---|---|---|
| AST 即用即弃 | worker 内 `parse → collect → classify → 只把候选（约 pool/文件数 ≈ 4 条/文件）传回主线程` | 单 worker 常驻内存 ≤ 30MB |
| worker 池 | `min(4, os.cpus().length - 1)`，按文件分片，主线程只聚合 | 1 万文件 RSS ≤ 200MB |
| 增量索引 | 以 `(mtime, size, sha1头8K)` 为指纹的 NDJSON 分片索引；保存单文件只重扫该文件 | 单文件保存 → 重新出结果 ≤ 50ms |
| 背压 | 主线程 heap 水位 150MB 暂停派发，300MB 强制 `global.gc` + 分片落盘 | 不 OOM |

**不做**的事：不引入 SQLite / 原生模块（打包体积 + 跨平台编译风险），NDJSON 分片足够（实测 1495 文件索引约 3MB）。

### 风险与回退

- 风险：worker 与主线程之间传候选结构需保持可序列化，别把 AST 或函数带过去（会被结构化克隆拒绝）。
- 回退成本：**低**。流式是纯内部实现，接口不变。

## D4 · 键命名的 A/B 校准：半天，不阻塞 M1

不是"要不要做"，而是"怎么控制成本"：D1 的 AI 层需要 prompt 校准，否则命名风格漂移。

- 样本：从本次 1385 条真实词条（vben 914 + adp 471）里按"高频 + 长文本 + 富文本"分层抽 20 条。
- 评测维度：① 可读性（另一个模型盲评 1–5 分）② 稳定性（改 3 个字后键是否不变）③ 长度（≤ 40 字符比例）。
- 通过线：可读性 ≥ 4.0 且键长超限率 ≤ 5%。
- 时间盒：半天。**不通过就把 AI 层降级为拼音**，M1 照常开工。

## 汇总

| 决策 | 结论 | 回退成本 | 何时定死 |
|---|---|---|---|
| D1 键命名 | 结构 + AI + 拼音三层，键写入即冻结，禁哈希 | 中 | **M1 第 1 周** |
| D2 句子建模 | 富文本整体抽取 + 索引占位符，宁缺勿错 | 低 | M1 第 1 周 |
| D3 内存 | 流式 + worker 池 + 增量索引 + 背压 | 低 | M1 第 2 周 |
| D4 命名校准 | 20 条样本、半天、不通过降级拼音 | 无 | M1 第 1 周内 |
