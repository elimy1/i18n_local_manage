## 1. D1：键命名改成「结构 + 语义 + 拼音兜底」

### 改了什么

新增 `spike/src/keys.mjs`，键模板 `<namespace>.<scopePath>.<role>.<slug>`：

| 段 | 来源 | 例 |
|---|---|---|
| `namespace` | 配置，默认 `app` | `app` |
| `scopePath` | 源文件相对路径：去 `src/`、去 `index`、`views`→`pages`、camel→kebab，最多保留 4 段 | `pages.demos.vben-alert.prompt` |
| `role` | AST 位置：属性名 / 对象键名 / callee 末段 / `text` | `placeholder` |
| `slug` | ①含 ASCII 取词 ②纯中文走 `pinyin-pro` ③序号兜底 | `qing-chu` / `please-enter` |

三条硬规则有没有真落地，看代码就是三条：

- `KeyRegistry.keyFor()` 先查 `scope|role|value` 命中即返回 → **键一旦写入就冻结**；
- `slug` 段是唯一允许 AI 接管的部分，结构段永不改；
- 删掉了 `sha1` 内容哈希分支（原 `auto.c1a2b3` 那套）。

配套修的两个坑：

1. **键表会残留死键**：文件如果没过后置语法闸，它的键已经写进注册表却没有任何代码引用。加 `keyRegistry.prune(used)`，只保留 `records` 里真实出现的键（vben 1628→1312）。
2. **同文不同键**：这是结构性命名的必然代价，见 §5。

### 实测

| 指标 | 改造前 | 改造后 |
|---|---|---|
| vben 键总数 | 914 | **1312** |
| 其中内容哈希键 | 681（**74.5%**） | **0** |
| vben 平均键长 | —（`auto.` + 6 位哈希） | 43 |
| vben 最长键 | — | 60 |
| 去重倍数（改写处/键） | 2.57× | 1.79× |
| adp 键总数 | 471 | 636 |
| adp 平均键长 | — | 42 |

真实键对比（同一条串，两套命名）：

```
auto.c1a2b3                    →  app.pages.demos.vben-alert.prompt.placeholder
auto.c9f8e1                    →  app.pages.demos.vben-alert.prompt.placeholder-2
auto.a                         →  app.demos.vben-alert.prompt.alert
auto.a-a-a-a                   →  app.components.article-list-content.text
```

**冻结验证**：同一份 keys 文件跑第二次 codemod，`keys frozen: 1312 (live 1312)` —— 0 个新键、0 次重命名。这是 D1 最重要的验收项，因为"每次扫描都换键"会让所有已翻译语言失效。

### 已知不足

- 少部分键被截断成 `...text`（路径+role 已经超过 48 字符），可读性靠路径本身撑着；
- 同一句文案出现在 10 个文件会得到 10 个键，去重倍数从 2.57× 掉到 1.79×。这是"可读、可定位"换"少键"的主动取舍，跨文件语义合并留给 M2 的"近似重复建议"功能。

## 2. D2：富文本整体抽取（React 侧已跑通）

### 改了什么

`spike/src/parse.mjs`：

- 新增 `INLINE_TAGS`（a/b/span/strong/em/code/i/s/small/u/mark/bdi/br）与 `isInlineJsx()`；
- JSX 句子合并循环现在会**吞掉内联元素**，产出新 kind `jsx-rich`，并生成一份 `meta.rich`：
  ```json
  { "template": "<0>{v0}</0> 发布在 <1>{v1}</1> <2>{v2}</2>",
    "values": [{ "name": "v0", "code": "owner" }, ...],
    "tags":   [{ "open": "<a href={href}>" }, ...] }
  ```
- **编号只算一遍**（`serializeRich`），catalog 字符串和生成的代码共用同一份编号，从结构上不可能对不上；
- 遇到 `LogicalExpression` / `ConditionalExpression` / 内嵌 JSXElement **一律断开**，不跨条件、不跨组件；
- 富文本区间会吞掉其内部更小的 item（否则同一段落会被抽取两次）。

`spike/src/codemod.mjs`：`jsx-rich` 改写成

```jsx
<Trans i18nKey="app.components.article-list-content.text"
       values={{ v0: owner, v1: href, v2: dayjs(updatedAt).format('YYYY-MM-DD HH:mm') }}
       components={[<a href={href} />, <a href={href} />, <em />]} />
```

并自动补 `import { Trans } from 'react-i18next'`，同时保留原有缩进（否则改完的代码会粘成一行，review 时非常刺眼）。

### 实测（ant-design-pro）

- 识别出 **59 个富文本单元**；改造前这些位置只会抽出 `"发布在"` 这种碎片；
- 完整的改写产物：

  ```jsx
  <div className={styles.extra}>
    <Avatar src={avatar} size="small" />
    <Trans i18nKey="app.components.article-list-content.text" values={{ v0: owner, v1: href, v2: dayjs(updatedAt).format('YYYY-MM-DD HH:mm') }} components={[<a href={href} />, <a href={href} />, <em />]} />
  </div>
  ```
- adp 改写 679 处、词条 636、conflicts 0、post-parse 0；
- 启发式审计：`codeLeak 0.15%`、`fragment 0.59%`、`doubleWrap 0`、`hashKey 0`，合计 **0.74%**。

### 没做的部分（要写进 M1 计划）

- **Vue 侧富文本没做**。`<i18n-t>` 需要生成 `<template #0>` 插槽，比 React 的 `components=[...]` 复杂一档；当前 Vue 仍按纯文本抽，vben 的 `发布在` 类碎片依然存在（2 条/2351）。
- `<Trans>` 目前假设宿主项目已有 react-i18next（真实项目多数有，但下一步要在 `plan` 里检查依赖，否则注入了不存在的包名）。

## 3. D3：worker 池 + 增量索引 —— 结论需要修正

### 改了什么

新增两个文件：

- `spike/src/scan-worker.mjs`：worker 内 `read → parse → collect → classify`，**只回传候选 item**（AST 不出线程）；
- `spike/src/scan-pool.mjs`：有界池（默认 `min(4, cpus-1)`）+ NDJSON 增量索引 + 主线程只做聚合。

增量索引按 `(rel, mtimeMs, size)` 命中，命中直接复用上次的 item 列表，不解析、不读 AST。

### 实测（vue-vben-admin，1495 文件 / 5721 候选）

| 模式 | 总耗时 | 文件/秒 | 峰值 RSS | 主线程 heap |
|---|---|---|---|---|
| 单线程 in-process（旧） | 1016 ms | 1471 | 292 MB | 159 MB |
| worker × 1 | 1346 ms | 1110 | **236 MB** | 9 MB |
| worker × 2 | 882 ms | 1695 | 265 MB | 10 MB |
| worker × 4 | **692 ms** | **2196** | **338 MB** | 15 MB |
| 增量（全部命中） | **77.5 ms** | 19299 | **45 MB** | 16 MB |
| 增量（改 1 个文件） | 208 ms | — | 153 MB | 16 MB |

索引体积：**1.13 MB / 1495 文件**（规划估 3 MB，实际更小）。

### 结论修正（这是本轮最重要的发现）

**「AST 即用即弃」被验证了**：主线程 heap 稳定在 9–16 MB，和扫多少文件无关；只有 2586 条候选留在内存里。这条不变。

**「worker 池」没有被验证，反而变差了**：

- 单 worker（1346 ms）比单线程 in-process（1016 ms）**慢 32%**，因为跨线程结构化克隆的代价大于解析本身；
- 4 worker 才快 1.47×，但峰值 RSS 338 MB，**超出 200 MB 预算 69%**；
- 每个 Node isolate 的基线就是 40–80 MB，4 个 worker 光空转就吃掉 250 MB 量级；
- 增量命中时 RSS 只有 45 MB —— 说明**真正省内存的是索引，不是线程**。

因此 D3 修订为：

| 场景 | 选择 |
|---|---|
| CLI / 批处理 / CI | **in-process 单线程 + 增量索引**。快、省、无跨线程开销 |
| 扩展里的全量扫描（要保宿主不卡） | worker 池，**默认 2 个**，heap 水位 150 MB 暂停派发 |
| 单文件保存 | 索引精确失效单文件，实测解析 **20.6 ms**（≤50 ms 达标） |

验收口径也要改：不是"1 万文件 RSS ≤200 MB"，而是"**主线程 heap ≤50 MB 且增量命中率 100% 时冷启动 ≤100 ms**"。前者靠 isolate 数量根本压不下来，后者才是用户体验真正感知的。

## 5. 这轮暴露的新问题（进 M1 backlog）

1. **键膨胀**：结构命名 + 逐文件 scope ⇒ 同文案多键。需要在 M2 做"语义重复合并"，而不是回退到哈希。
2. **键名可读性的天花板在 slug**：目前纯中文串只有拼音（`bian-ji`），英文团队仍会觉得像乱码。D4 的 AI 命名评测要在 M1 第 1 周补。
3. **`<Trans>` 依赖假设**：必须检测项目是否装了 `react-i18next`，否则要降级成 `t()` + `<0>` 组件数组的等价写法。
4. **Vue 富文本缺口**：`<i18n-t>` 生成器还没写，vben 的句子碎片没有真正消失。
5. **索引失效粒度**：目前按 mtime+size，改内容但保持大小（极少数）会漏判；上 `sha1(头 8K)` 即可，代价可忽略。
