# M1 交付说明

M1 的目标不是"功能列表"，而是**一个能在真实项目上跑、跑两遍不会出事、并且能被验证的插件**。以下是当前仓库的真实状态，数字都来自实测。

## 1. 交付物

| 位置 | 内容 |
| --- | --- |
| `packages/core` | 纯 TS 引擎，零 `vscode` 依赖：解析、打分、改写、键注册表、覆盖率、词条读写 |
| `packages/adapters` | 框架适配：`next-intl` / `react-i18next` / `vue-i18n` / `generic`，从 `package.json`（含 monorepo 的 `apps/*`）自动识别，决定 import 别名与词条目录 |
| `packages/cli` | `scan` / `apply` / `report`，退出码可供 CI 使用 |
| `packages/vscode` | 扩展：树视图、CodeLens、diff 预览、`WorkspaceEdit` 应用、覆盖率报告 |
| `packages/vscode/i18n-codemod-0.1.0.vsix` | 可安装产物，2.85 MB / 867 个文件，已内联 core、adapters 与 20 个运行时依赖 |
| `spike/` | M0 度量脚本，保留以便复现 `docs/03-Spike结果.md` 的数字 |
| `docs/01`–`docs/05` | 规划、Spike 方案、Spike 结论、决策记录、决策落地记录 |

## 3. 本轮修掉的六个真实缺陷

前两个是端到端跑出来的，后三个是写幂等测试时暴露的。

1. **键表被清空（数据丢失）**。`prune()` 只保留本次运行实际用到的键，第二次运行几乎没改动，于是把上次冻结的 1275 个键全删了。修法：`KeyRegistry` 记录 `minted` 集合，`prune` 只删"本次新造且本次未用"的键，历史冻结键永不删。否则下次运行会给同一个字符串发新键——静默改名，是这类工具最不可接受的失败模式。
2. **覆盖率假零（度量失真）**。`coverageFromScan` 对已改写成 `t("app.x")` 的候选重新打分，key 自然是低分，于是全部不计入 extracted。修法：`meta.wrapped === true` 直接算作已受管文案，只对未包裹的跑 `isCopy`。
3. **Vue 模板里的 key 被误判为死键**。`{{ $t('x') }}` 在模板表达式里，脚本收集器看不见，于是每个模板键都成"死键"（418 个误报）。修法：`collectTemplateCalls` 把插值/指令表达式当表达式解析，收集其中的 i18n 调用并把 offset 换算回 SFC。
4. **重复注入 import**。第二次运行时重复插入 `import { useI18n }` 与 `const { t } = useI18n()`——重复绑定，文件直接编译不过。修法：注入点检查已存在同名绑定，存在则跳过。
5. **把 `t()` 参数里的字面量抽出来**，生成 `t("a", { v0: on ? t("b") : t("c") })` 的嵌套调用。修法：`planFile` 统一以 `classify().translatable` 为准（`not-copy` 跳过），偏移指纹闸先于打分执行，避免把漂移写成"不是文案"。
6. **富文本键被报成死键（adp 上 50 个）**。`<Trans i18nKey="app.x">` 的键写在 JSX 属性里，属性名不在可译清单、值又是纯 key，扫描器根本不收——于是每个富文本键都"没人引用"。修法：`i18nKey`（React）与 `<i18n-t keypath>`（Vue）作为**已包裹的 key 引用**入池。这是 M1 最后一处度量失真。

## 4. 与 M0 结论的差异

- 键命名：哈希键从 74.5% 降到 **0**，键表 1277 个，长度中位数 43 字符。
- 覆盖率：M0 只算到"能不能扫"，M1 才第一次得出可信的 97.8%——前提是修掉上面第 2、3 个 bug。
- 幂等：M0 没测。M1 把它变成硬约束并写进测试（第二次 apply 必须零编辑）。

## 5. 已知缺口（M2 之前）

| 缺口 | 影响 | 计划 |

| Vue 富文本 `<i18n-t>` 未实现 | Vue 项目的富文本句子仍会碎片化 | M2 第 1 周 |
| Options API 组件跳过 | Vue2 迁移场景改写率低 | 按需求排期 |
| 无 AI 命名 | 键名可读但不如人工/AI 命名 | M2 评测（D4） |
| 扩展无增量索引 | 大仓库每次全量扫（内存已达标） | M2 |
| 无 GitHub Action | 团队守门只能靠 CLI | M2 |
| 未做真实 VS Code 手测 | 集成测试用 stub，UI 细节未验 | 需要一台带 GUI 的机器 |

## 6. 复现

```bash
pnpm install --ignore-scripts

node scripts/build.mjs        # core → adapters → cli → vscode，单进程四份 program
node scripts/test.mjs         # core 27 + adapters 10 + 扩展集成断言，全部单进程

node packages/vscode/scripts/package.mjs

node packages/cli/dist/index.js apply corpus/vue-vben-admin --keys out/keys.json --catalog out/locales
node packages/cli/dist/index.js report corpus/vue-vben-admin --catalog out/locales/zh-CN.json
```

`scripts/build.mjs` 与 `scripts/test.mjs` 直接调 TypeScript API，不走 `pnpm -r run`——
后者每个脚本都要 spawn 一个 shell，在本环境会被拒（`spawn EPERM`）。

环境备注：本机没有可用的 `pnpm` 全局安装，用的是 DSH 自带运行时
（`node v24.21.0` + `pnpm 11.28.5`）；沙箱禁止带管道 stdio 的子进程，所以测试用
`node:test`、打包用"编译后拷贝 + yazl 重打包"而不是 esbuild/vitest。
