# 仓库与版本控制

回答两个问题：**哪些内容必须进 git**、**哪些绝不能进**。文末给了初始化/提交/打标签的完整命令。

## 1. 结论先看

| 类别 | 进 git？ | 现状大小 | 理由 |
| --- | --- | --- | --- |
| `packages/*/src`、`test`、`package.json`、`tsconfig*` | ✅ 必须 | 0.2 MB | 产品本体 |
| `scripts/`（build / test 入口） | ✅ 必须 | 6 KB | 没有它别人构建不了 |
| `docs/`（01–07） | ✅ 必须 | 0.2 MB | 决策与指标是资产，不是附件 |
| `spike/src` + `spike/labels` | ✅ 必须 | 0.15 MB | 指标可复现的前提：脚本 + 人工标注都在 |
| `spike/package.json` / `pnpm-lock.yaml` | ✅ 必须 | 90 KB | 锁定当时的依赖版本，否则数字无法复现 |
| `README`、`LICENSE`、`CHANGELOG`、`.gitignore`、`.gitattributes` | ✅ 必须 | 30 KB | 项目门面与行为约束 |
| `pnpm-lock.yaml`（根） | ✅ 必须 | 60 KB | 可复现安装 |
| `.npmrc` | ⚠️ 建议改后再提交 | 120 B | 见 §4 |
| `node_modules/` | ❌ | 211.9 MB | 可安装恢复 |
| `corpus/`（三个克隆仓库） | ❌ | 14.0 MB | 别人的代码，且可重新 clone |
| `out/`、`spike/out/` | ❌ | 20.4 / 11.9 MB | 跑一次就有，含中间 JSON 与 e2e 副本 |
| `dist/`、`.test/`、`*.tsbuildinfo` | ❌ | — | 构建产物 |
| `*.vsix`（2.85 MB） | ⚠️ 不算源码 | — | 作为 **Release 资产**，不进 git |
| `packages/vscode/.stage/`、`*.base.vsix` | ❌ | — | 打包中间态 |

一句话：**进 git 的是"人写的、且不能靠命令重新生成"的东西**；能被 `pnpm install` / `node scripts/build.mjs` / 重新 clone 恢复的，一律不进。

## 2. 必须提交的清单（逐项）

### 2.1 源码与工程配置

```

tsconfig.base.json

packages/adapters/{package.json,tsconfig*.json,src/**,test/**}

scripts/test.mjs
```

`packages/vscode/test/fixture/**` 必须提交：那是"改写正确性"的字节级样本，缺了集成测试就跑不了。已在 `.gitattributes` 里标 `-text`，防止行尾被转换。

### 2.2 文档

```
docs/01-技术规划.md      竞品与架构决策
docs/02-Spike验证方案.md  五个带阈值的假设

docs/06-M1-交付说明.md    M1 交付与验证
docs/07-安装与使用.md     安装、日常流程、排错

这些不是"写完就丢"的会议记录：`03` 里的每个数字都能用 `spike/` 重跑出来，`04` 里每条决策都写了回退成本。丢了它们，后面的人会重新争论一遍。

### 2.3 度量脚本与标注

```

`labels` 是**人工真值**，重新生成只能生成抽样、生成不了标注。它决定了 H1（P 91.3 / R 82.3）这个结论能不能被复核，属于不可再生资产，必须进。

### 2.4 根级门面

`README.md`、`.gitignore`、`.gitattributes`、`.npmrc`（见 §4）、`spike/package.json` + `spike/pnpm-lock.yaml`。

## 3. 绝不能提交的（以及为什么）

| 路径 | 大小 | 不进的理由 | 恢复方式 |
| --- | --- | --- | --- |
| `node_modules/` | 211.9 MB | 可安装；且含平台相关二进制 | `pnpm install --ignore-scripts` |
| `corpus/` | 14.0 MB | ant-design-pro / vue-vben-admin / ai-chatbot 的浅克隆 | `git clone --depth 1 <url>`（国内走 `ghproxy.net` 前缀） |
| `out/` | 20.4 MB | CLI 的 keys/catalog/e2e 副本/日志 | 重跑 `apply` |
| `spike/out/` | 11.9 MB | 扫描 JSON、改写结果、评审表 | 重跑 `node src/scan.mjs` |
| `dist/`、`.test/` | — | 编译产物 | `node scripts/build.mjs`、`node scripts/test.mjs` |
| `*.vsix` | 2.85 MB | 二进制发布物，每次构建都变；进 git 会让历史迅速膨胀 | 见 §4 |

**特别提醒 `out/`**：这个仓库里的 `out/` 是**本项目自己的**跑批产物，所以忽略。但你用这个插件去改**业务项目**时，`out/keys.json` 和词条文件必须提交——见 §5，两者语义完全不同。

## 4. 发布物：vsix 放哪

vsix 不该进 git，但必须可获取。三种做法，按推荐顺序：

1. **GitHub Release 附件**（推荐）

```powershell
# 打标签、推送、附上产物
git tag v0.1.0
git push origin main --tags
gh release create v0.1.0 packages/vscode/i18n-codemod-0.1.0.vsix --title "v0.1.0" --notes "M1 MVP"
```

2. **VS Code Marketplace**：`vsce publish`（需要 publisher 账号；本沙箱里 vsce 无法 spawn npm，只能在正常机器上跑）

3. **内网制品库**：把 vsix 传到 Nexus/OSS，README 里给下载链接

产物是可重建的：`node packages/vscode/scripts/package.mjs` 一条命令重出，所以"丢了"不是风险。

### `.npmrc` 要先改

现在根 `.npmrc` 是：

```ini
node-linker=hoisted
shamefully-hoist=true
strict-peer-dependencies=false
registry=https://registry.npmmirror.com/
```

`registry` 这行是**本机环境**的产物（国内镜像）。公开仓库里硬编码它，会让海外贡献者的安装走镜像。建议提交前删掉这行，把镜像说明写进 README 的"国内加速"小节；`node-linker=hoisted` 保留（Windows 下 pnpm 的 junction 与 Node ESM 解析不兼容，平铺是必需的）。

## 5. 别混淆：业务项目里该提交什么

用这个插件改**你自己的项目**时，规则相反——生成物恰恰是最该提交的：

| 文件 | 提交？ | 为什么 |
| --- | --- | --- |
| `out/keys.json`（键注册表） | ✅ **必须** | 它是"键已冻结"的唯一凭据。丢了它，下次提取会给同一句文案发新键 = 静默改名，翻译记忆库全断 |
| `src/locales/zh-CN.json` 等词条 | ✅ **必须** | 译文来源 |
| 被改写的源码 | ✅ 必须 | 就是这次改动的成果 |
| `out/*.log`、临时 diff | ❌ | 本地调试产物 |

建议把 keys 文件放到版本控制可见的位置（例如 `i18n/keys.json`），而不是默认的 `out/`——`out/` 在很多项目里本来就被忽略：

```jsonc
// .vscode/settings.json
{ "i18nCodemod.keysFile": "i18n/keys.json" }
```

## 6. 命令：从零到第一次提交

```powershell
cd D:\i18n_local_manage

# 1) 已初始化（本次已执行），确认分支
git branch --show-current          # main

# 2) 提交前自查：只应看到源码、文档、脚本
git add -A
git status --short | Measure-Object -Line

# 3) 确认没有任何大目录漏进来
git ls-files | Select-String -Pattern 'node_modules|corpus/|/dist/|\.vsix$'
#    应当无输出

# 4) 身份（只需一次；用你自己的）
git config user.name  "your-name"
git config user.email "you@example.com"

# 5) 首次提交
git commit -m "feat: i18n codemod MVP — typed core, adapters, CLI, VS Code extension"

# 6) 远端
git remote add origin <你的仓库地址>
git push -u origin main
git tag v0.1.0 && git push origin v0.1.0
```

### 提交信息约定

`feat:` / `fix:` / `docs:` / `chore:` 前缀即可，不需要工具链。这个仓库的价值在 `docs/` 的决策链，提交粒度按"一个可验证的改动"切：

- `fix(core): 富文本 i18nKey 被报成死键`
- `feat(adapters): monorepo 里向 apps/* 一层查找 i18n 依赖`
- `docs: 安装与使用、仓库清单`

## 7. 分支与版本

| 项 | 建议 |
| --- | --- |
| 主分支 | `main`，始终可构建、测试绿 |
| 功能分支 | `feat/<short-name>`，合并前 `node scripts/test.mjs` |
| 版本号 | 语义化；扩展 `package.json` 的 `version` 与 tag 一致（当前 `0.1.0`） |
| 变更记录 | 每次发版在 `packages/vscode/CHANGELOG.md` 加一节 |
| 里程碑 | `v0.1.0` = M1 MVP；`v0.2.0` 计划 Vue `<i18n-t>` + AI 命名 |

### CI 提示（GitHub Actions）

仓库里**没有** workflow 文件，因为本环境无法验证它。加的话最小可用版本：

```yaml
name: ci
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 11 }
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: pnpm }
      - run: pnpm install --ignore-scripts
      - run: node scripts/build.mjs
      - run: node scripts/test.mjs
```

注意：CI 上可以直接用 `pnpm -r run build`（Linux 没有本机的 spawn 限制），但用 `scripts/*.mjs` 两边行为一致，更省心。

| 项 | 当前 | 上限建议 |

| git 跟踪文件 | 94 个 / **0.61 MB** | < 5 MB |
| 单文件最大 | 约 60 KB（`docs/01`） | < 1 MB |

超过这些阈值通常意味着误提交了 `out/` 或 `corpus/`。查一下：

```powershell
git ls-files -s | ForEach-Object { ($_ -split '\s+')[1] } |
  git cat-file --batch-check='%(objectsize:disk) %(rest)' |
  Sort-Object { [int]($_ -split ' ')[0] } -Descending |
  Select-Object -First 10
```
